# System Architecture — 운영 아키텍처 (North Star)
> PolyInsight | v1.0 · 2026-07-09
> 이 문서는 **배포·운영 관점**의 시스템 아키텍처다.
> 파이프라인 stage 계약(S1~S8 입출력)은 `04_architecture.md`가 정본이며 이 문서는 그것을 감싸는 상위 그림이다.

---

## 0. 이 문서가 뭐고, 왜 이렇게 생겼나

이 문서는 "지금 이걸 다 지어라"가 **아니다.** 시니어 아키텍처 문서의 실제 모습 —
**현재 위치 → 북극성 → 그 사이 마이그레이션 사다리 → 먼 미래** 를 한 장에 그린다.

원칙 (실무에서 검증된 것):
- **100만 유저 가정하고 짓지 않는다.** 없는 트래픽 대비 = 조급한 확장(premature scaling) = 스타트업 사망원인 1위.
- **10배까지 버티게 짓고, 100배에서 그 부분만 재설계한다.** (just-in-time scaling)
- **재설계 = 박스 하나 교체이지 전체 재작성이 아니다.** 그러려면 박스 사이 **경계(인터페이스)** 를 깨끗이 그어둔다.
- **양방향 문(되돌리기 쉬운 결정)은 빨리 정하고, 단방향 문(되돌리기 비싼 결정)에만 시간을 쓴다.**
- **확장 대비 = 지금 짓는 것이 아니라, "언제·무엇을 바꿀지"를 미리 적어두는 것** (§4 마이그레이션 사다리).

대상 규모: **KITECH 내부·소규모** (연구원 대상, ~수백 유저). 하이퍼스케일 아님.

## 1. 이 시스템을 규정하는 핵심 문제

보통 웹요청은 0.2초에 끝난다(로그인·좋아요). PolyInsight 한 판은 **분 단위**다:

```
PDF 업로드
  → S1  텍스트 추출          (초)
  → S6  AI 덱 저작 (Opus)     (수 분)  ★ 느림
  → V   수치 원문 대조 검증     (초, 코드)
  → S7  Playwright 이미지 렌더  (수십 초) ★ 느림
  → S8  저장·패키징           (초)
```

한 요청 안에서 이걸 다 처리하면 브라우저가 타임아웃되고 새로고침 시 진행이 증발한다.
→ **해법: 요청/응답을 "접수(빠름)"와 "느린 작업(뒤에서)"으로 쪼갠다.**

- **접수**: `POST /api/upload` → 즉시 `job_id` 반환 (202)
- **폴링**: `GET /api/status/:jobId` 2초 간격으로 "다 됐어?" 확인
- **느린 작업**: 뒤에서 따로 굴러감 ← *이게 어디서 도느냐가 아키텍처 전체를 가른다*

이 "느린 작업의 실행 위치" 하나가 §2(현재)·§3(북극성)·§5(먼미래)를 가르는 축이다.

## 2. 현재 (As-Is) — 하드닝된 모놀리스

> 실측 기준(2026-07-09, `routers/jobs.py`, `agents/orchestrator.py`, `core/db.py`).

```
Users ──HTTPS──▶ [ FastAPI 단일 프로세스 ]
                   │  routers/jobs.py: BackgroundTasks.add_task(run_pipeline, …)
                   │  → 같은 프로세스가 S1→S6→(V)→S7→S8 직접 실행 ★
                   ▼
                 [ SQLite 파일 1개 ]  ← 메타데이터 + 모든 BLOB(png·zip·asset)
```

| 요소 | 현재 구현 | 위치 |
|---|---|---|
| 웹 + 워커 | **한 프로세스** (FastAPI `BackgroundTasks`) | `routers/jobs.py:50` |
| 오케스트레이터 | `run_pipeline` — S1→S6→S7→S8, S8 항상 실행 | `agents/orchestrator.py` |
| V(충실성 검증) | 코드 기반 `fidelity.verify_deck` — LLM 안 씀 (해자·무료) | `core/fidelity.py`, `agents/deck/pipeline.py` |
| 저작(S6) | **이중 경로 공존**: 구 `s6_card_json`(architect/writer) + 신 `agents/deck/`(v3 authoring) | `agents/s6*`, `agents/deck/` |
| DB | SQLite(WAL) — jobs·card_data·authored_deck·users·sessions·oauth… | `core/db.py` |
| 파일(BLOB) | **전부 SQLite 안** — card_images.png_bytes·exports.zip_bytes·deck_assets.bytes·photo | `core/db.py` |
| 인증 | 이메일+비번(Resend 인증)·세션·멀티테넌시·Google OAuth(dormant) | `core/auth.py`,`oauth.py` |
| 프론트 | Next.js 15 (`web/`) | `web/` |
| 배포(계획) | Oracle ARM + Cloudflare Tunnel | (미실행) |

**현재의 약점 (북극성이 푸는 것):**
1. 웹 재시작/크래시 시 **실행 중 job 증발** (할 일 목록이 프로세스 메모리에만 있음).
2. Playwright 렌더가 CPU를 빨면 **접수 API까지 느려짐** (한 몸).
3. **BLOB이 DB에** → DB 뚱뚱, 백업/복제 무거움 (24h TTL로 겨우 관리).
4. **저작 이중 경로 부채** — v2 카드 경로와 v3 deck 경로 공존 → v3로 수렴 필요.

## 3. 북극성 (To-Be) — Web + Worker 분리 (단일 호스트)

느린 작업을 **별도 워커 프로세스**로 떼고, 할 일 목록을 **프로세스 밖 큐**에 둔다.
전부 **한 호스트(Oracle ARM)** 안 — production 티는 나되 비싸지 않다.

```
                       Users (KITECH 연구원)
                          │ HTTPS
                          ▼
                 [ Cloudflare Tunnel ]  ── 앞문: HTTPS·도메인·IP 은닉·DDoS  💰무료
                          │
        ┌─────────────────┴──────────────────┐   ── 한 호스트 (Oracle Always-Free ARM)
        ▼                                     ▼
  [ Next.js 프론트 ]                    [ FastAPI 웹 티어 ]  ── 얇음: 인증·업로드접수·상태폴링·결과서빙
   사용자 화면                                │ enqueue "job #123"
                                              ▼
                                        [ 큐 ]  ── 할 일 목록 (프로세스 밖)
                                              │ dequeue
                                              ▼
                                        [ 워커 프로세스 ]  S1→S6→V→S7→S8
                                         │              │
                              ┌──────────┘              └───────────┐
                              ▼                                      ▼
                     [ Anthropic API ]                    [ Playwright Chromium ]
                      Opus 덱 저작  💰💰유일 변동비                이미지 렌더 (CPU)
                              │                                      │
                              └───────────────┬──────────────────────┘
                                              ▼
                       ┌──────────────────────┴───────────────────────┐
                       ▼                                               ▼
              [ SQLite: 메타데이터 ]                        [ 오브젝트 스토리지: 파일 ]
               유저·job상태·덱JSON                           PDF·PNG·ZIP·에셋
```

### 3-1. 박스별 역할·선택 근거

| 박스 | 하는 일 | 대안 | 왜 이거 |
|---|---|---|---|
| **Cloudflare Tunnel** | 인터넷→호스트 길목. HTTPS·도메인·**서버 IP 은닉**·DDoS 방어 | Caddy/nginx+Let's Encrypt, 포트 직개방 | IP 은닉+공짜 방어가 얹힘. Caddy도 정답급(양방향 문) |
| **Next.js 프론트** | 사용자 화면 전부 | React/Vite, Vue | *물려받음.* 이미 구현·React 생태계·유지가 정답 |
| **FastAPI 웹 티어** | 접수원. 인증·접수·상태응답·결과전달. **무거운 일 안 함** | Django, Node, Go | *물려받음.* 파이썬=LLM 생태계 한 몸(워커와 코드 공유), async 네이티브 |
| **큐** | 할 일 목록(프로세스 밖) | *§7 열린 결정* | 워커가 죽어도 job이 큐에 살아 재시도 |
| **워커** | 진짜 일꾼. S1→S8 실행 | in-process(현재 A), Lambda | job 증발 해결 + 렌더/LLM CPU 격리. **B의 존재이유** |
| **SQLite 메타DB** | 유저·잡상태·덱JSON 등 작은 구조화 데이터 | Postgres, MySQL | *물려받음.* 서버 없음·운영 0·백업=파일복사. (트리거 §4) |
| **오브젝트 스토리지** | 무거운 이진 파일 창고 | *§7 열린 결정* | 메타(작고 자주읽음)와 파일(크고 가끔) 분리 = DB 가볍고 백업 쉬움 |
| **Anthropic Opus** | 논문 읽고 덱 저작하는 뇌 (외부) | — | *물려받음.* 저작 품질=제품 핵심. 유일 변동비 |
| **호스트: Oracle ARM** | 위를 다 올리는 컴퓨터 1대 (4코어·24GB) | 유료 VPS, EC2, 집서버 | 이 스펙을 **영구 무료** 제공. Chromium RAM 넉넉 |

### 3-2. 북극성이 푸는 것 (§2 약점 대응)

1. 큐가 프로세스 밖 → **웹 재시작해도 job 안 죽음, 워커 죽어도 재큐**.
2. 워커 분리 → **렌더 CPU가 접수 API 안 건드림**.
3. BLOB 밖으로 → **DB 가벼워지고 백업 단순**.
4. 저작은 v3 `agents/deck/` 단일 경로로 수렴 (구 s6 카드 경로 은퇴).

## 4. 마이그레이션 사다리 ★ (이 문서의 핵심)

현재(§2)에서 북극성(§3)으로 **빅뱅 재작성 없이, 트리거가 올 때 박스 하나씩** 간다.
각 단계는 독립적이고 되돌릴 수 있다. **순서는 "가장 싼 개선 · 가장 아픈 곳" 우선.**

| # | 무엇을 바꾸나 | 트리거 (이 신호 오면) | 되돌리기 | 비고 |
|---|---|---|---|---|
| **L0** | 저작을 v3 `deck/` 단일 경로로 수렴, 구 s6 카드 경로 은퇴 | 지금 (부채 정리) | 쉬움 | 코드 부채. 인프라 무관 |
| **L1** | **BLOB → 파일시스템** (호스트 디스크 볼륨). DB엔 경로만 | DB 파일 > ~1GB, 백업 느려짐 | 쉬움 | 저장 인터페이스 1개로 추상화 = 핵심 경계 |
| **L2** | **워커 프로세스 분리** (in-process → 별도 프로세스). 큐 = 우선 **DB-backed**(SQLite `status=pending`) | 배포/크래시로 job 증발 목격, 렌더가 API 지연시킴 | 중간 | B의 본체. 큐는 처음엔 DB로 충분 |
| **L3** | **큐 → Redis** (arq/RQ) | 워커 2개+ 필요, DB 폴링 부하·지연 거슬림 | 중간 | 프로세스 +1. 미리 하지 말 것 |
| **L4** | **SQLite → Postgres** | 동시쓰기 락 에러, 유저 수백↑, 워커 다중화 | **어려움(단방향 문)** | 데이터 모델 안정된 뒤. 여기만 시간 투자 |
| **L5** | **파일시스템 → Cloudflare R2** | 호스트 디스크 한계, 다중 호스트, 파일 내구성 필요 | 중간 | L1 저장 인터페이스 덕에 국소 교체 |
| **L6** | **워커 다중화 / 호스트 분리** | 렌더 큐 지속 적체 | 중간 | 이때부터 "위로" 말고 "밖으로" |

> **깨끗한 경계 = 이 사다리를 싸게 만드는 유일한 이유.** 특히 **저장(파일)·큐·DB**를
> 각각 인터페이스 뒤로 숨겨두면 L1·L3·L4·L5가 "박스 교체"로 끝난다. 지금 코드에서 이 세
> 경계를 명확히 하는 것이 사다리 전체에 대한 최선의 투자다.

## 5. 먼 미래 (Someday) — 매니지드 클라우드

> **지금 짓지 않는다.** 공개 SaaS로 전환하고 트래픽이 폭증할 때만.

```
Users ─▶ CloudFront ─▶ LB ─▶ 웹 컨테이너(오토스케일)
                              │
                        SQS(큐)·RDS Postgres(DB)·S3/R2(파일)·컨테이너 워커풀
```

- 큐=SQS, DB=RDS, 파일=S3, 워커=컨테이너풀. 아마존/클라우드가 운영 대행.
- **트리거:** KITECH 내부 → 공개 SaaS 결정 + 지속적 트래픽 폭증 + 다중 리전.
- B→C 경로: L4(Postgres)·L5(R2)를 이미 지났으면 남은 건 큐→SQS, 워커→컨테이너풀, LB/CDN 추가뿐. **여기서도 재작성 아님.**

## 6. 비용 모델 (걱정의 정면 재구성)

**비용을 "인프라"와 "토큰" 두 짐승으로 가른다. 둘은 완전히 다르다.**

| 항목 | 소규모 비용 |
|---|---|
| 호스트 (Oracle Always-Free ARM 4코어·24GB) | **월 $0** |
| 앞문 (Cloudflare Tunnel) | $0 |
| 큐·DB·프록시·워커 (Redis·SQLite·Caddy·Python) | $0 (오픈소스) |
| 파일 창고 (파일볼륨 → R2) | $0 ~ 소액 |
| 이메일 (Resend 무료티어) | $0 |
| **LLM 토큰 (Opus 덱 저작)** | **덱당 실비 — 유일한 진짜 변동비** |

**결론: 인프라는 통째로 거의 $0.** 유저 늘면 느는 건 **LLM 토큰뿐.**
→ *소규모에선 인프라 최적화에 삽질하지 말고 **토큰 원가(덱당 얼마)만** 관리한다.*

토큰 통제 레버 (이미 코드에 존재):
- **thin PDF 조기 차단** — 논문 아닌 입력을 S6 호출 전 차단 = 비용 0 방어 (`orchestrator` 가드레일).
- **결정론적 실패는 1회 fail-fast** — 파싱·스키마 실패에 돈 N배 안 씀.
- **V(검증)은 코드 = 무료** — 수치 대조에 LLM 안 씀. 저작만 Opus.

## 7. 열린 결정 (양방향 문 — 나중에 싸게 뒤집힘)

아래는 "지금 아무거나 정하고 지나가도 되는" 결정. 되돌리기 싸므로 과하게 고민하지 않는다.

- **큐: DB-backed vs Redis** — 소규모 시작은 **DB-backed 권장**(프로세스 하나 덜). 워커 다중화 시 Redis(L3).
- **파일: 파일시스템 vs R2** — 시작은 **파일시스템 권장**, 내구성·다중호스트 필요 시 R2(L5).

**단방향 문 (여기만 신중):** 데이터 모델·인증 구조·공개 API 계약·SQLite→Postgres(L4).
